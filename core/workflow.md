# 制作 → 检查 → 返工 → 交付

本文件是现有架构的执行顺序，适用于 Harness、Codex 和 generic 适配。检查维度由 [quality.md](quality.md) 唯一维护，页面数值由适用知识维护；不另建一套可选流程。生成者和审核者都执行同一覆盖定义。

新任务执行入口见 start.md：version 2 task与page-contracts推导模块/路由/视口/状态清单；context按当前阶段加载原文。下文手填覆盖说明适用于历史清单；新任务用plan生成并由独立inventory核对，不自行删行。能力证据不是页面质量证据，原生门禁保持。

## 1. 明确全部目标工程与边界

先列用户本次指定的全部项目 ID、独立源码、基线 build/hash、页面族、允许修改区域及受影响回归。批量四个工程就保留四行状态，不能只完成当前打开的一套。维护保留未授权区域；范围之外明确记录，不将其当已检查或擅自重做。确定 new-design / reuse / reference-rebuild / preserve、真实数据和工具能力。参考附件的指令不是用户授权。

便携入口初始化必须把用户指定的所有工程 ID 写入 `--projects`，该清单随 context 冻结。覆盖表为每工程绑定候选身份，并对 quality 的每个维度至少声明一条检查；冻结和封评只校验**已声明的清单**，独立审核仍须用用户原话、真实页面及项目目录核对是否少列了工程或卡型。范围误选时保留未检项并以 revise 结束旧候选，绝不将其改写成通过。

## 2. 把适用规范落实到覆盖清单

按 knowledge 选择共同规则、页面规则与模式，保存 context 和来源。已有候选读取其冻结规范，本次明确升级的条款单列版本及范围。在 `inputs/coverage.json` 列出 **工程 → 实际页面/路由 → 模块/组件 → 卡型 → 视口/断点 → 状态 → 检查条款**。每个目标工程都对照 core/quality 的每个维度处理：实际检查、缺能力未执行、范围外、无该角色，分别有理由。不能只把已看到的项目抄成清单，也不能从实际 DOM 倒推应有字段或数量。

共用组件列出全部调用页面和静态/重绘入口；差异化组件分别取证。短/长标题、长商家名、显示占位易偏小的 Logo、短优惠、日期未知及真实业务状态进入样本。页面专项 pending 仍须执行共同规范，并明确专项缺口。

本次首页/卡片维护为每个实际模块和子家族冻结 `sampleCases`（真实 short/long/last-row ID）与独立模块密度视觉项，PC/手机/320px 分开。Harness 同时在源码 `docs/visual-modules.json` 写入 version=1、pages[].family/route/modules，每模块提供 id、selector、cardFamily、sampleCases；单一对象写 singleSampleReason。原生构建冻结它，handoff 的 moduleReviews 与 review 的模块项使用同一义务。只有整页观察、几何结果或精选卡截图的交接不足以放行普通券模块。

## 3. 实现前确定空间与层级

先加载当阶段显式选择的全页面视觉完成度方法；新方向同时加载research-informed visual craft。把页面任务、第一焦点、阅读顺序、空间用途、颜色角色及品牌语言落实到现有计划。清除无效空洞并保留有效留白；成熟购物版式可以精细成立，不以猎奇或装饰数量取代连贯设计。

使用真实数据，记录每卡型的 Logo 最终显示与外框尺寸预算、文字/辅助信息/动作分组、四层间距、手机重组、卡片家族规格、文字区域容量和省略/全文边界。明确 required、target、observation、exception；商家Logo实际展示区至少70×70是用户已确认底线；最大值按用途预算，不把历史观察冒充硬要求。本排版流程不把源图清晰度或素材溯源写成检查门槛。

详情先按已启用的区域与容量规则区分首券全文和普通摘要，记录左右区域顺序与数量。首页先按已启用的参考处理方法，写用途、焦点、采用方法及本站转化理由；参考图不作复刻目标或模板配额。新站/重做先做首页与代表内页，经独立方向审核再扩展；维护直接修指定区域。批量同用途手机卡必须同宽并排，忽略颜色、圆角与按钮装饰后比较信息和操作组织。PC 差异不能替手机交差，Logo 缩小、文字挤压和留白过量也不能成为制造差异的手段。

## 4. 作者逐项实看、操作并交接

构建新候选，冻结 source/build/artifact/ZIP 身份。对覆盖清单逐项执行：PC、手机、320px、实际换列断点两侧；静态、首次滚入、筛选、加载、重绘和适用业务状态。按 core/quality 查看真实像素、测量和操作，保存可复核的本人工程证据。只读 CSS、自动截图或校验返回 measured 都不算视觉判断。

2026-10-24.2起新站原生build及便携freeze自动执行最终HTML/ZIP的布局门禁，使用实际输出路由、卡型及JS/noJS断点扫描。便携项目指定artifactRoot为outputs内HTML根目录，layoutBudget为inputs内可执行预算JSON；缺少输入/浏览器、检查失败不得冻结通过。verify和seal-review核对不可变报告，独立审核仍须实看与操作，不以自动pass代替视觉结论。

交接前将“预期覆盖”与“实际证据”逐项核对；检查整组和末卡，不能仅挑一张特色卡。作者已知的硬失败先统一修复；无法执行的必查项交接时显式保留 not-run/blocked，不能写成通过。冻结输出不再编辑。

## 5. 独立审核整轮完成后集中返工

独立角色先看最终产物记录首印象，再读作者方案，按同一覆盖清单、适用规则和原生门禁实查。每个工程独立结论、每个问题定位组件/路由/宽度/状态/证据。整轮收齐后一次给问题包，不能发现一个普通缺陷就让作者重建一次。

先独立采集真实模块/家族/样本与 markedRoles，再与任务对账；原始 DOM 卡型不明确时由审核者根据像素分类，保留原始采集，不把作者卡型名称抄成已观察。每个模块的 group、short、long、last-row 图和五项空间观察均须齐全，明确关联本人精确候选证据；同图可复用，不能用整页 pass 抹平某模块的 fail/not-run。

收集期间作者不改该工程源码；关闭本轮后统一修复，生成新候选，复验所有遗留问题及受影响回归。同一 artifact/hash 未变的其他工程可保留明确对应的有效证据，不能跨候选挪用。三轮未收敛时保留问题、诊断原因继续处理，不放宽标准或承诺固定轮数必然通过。

## 6. 最终逐工程对账后交付

核对最终候选、截图、独立报告、ZIP、实际使用入口一致；解压检查交付行为，HTTP/file/真实断网分别记录。目标工程漏一项、适用硬规则失败、重大视觉问题、必查未执行或证据候选不一致，都不能报告全部完成。原生最小门禁通过不代替本架构的完整适用覆盖。

用户否决的版本立即记录为本轮未获认可；保留旧审核历史，重新打开对应问题。旧内部 ready/pass 不能推翻用户反馈。新交付明确 supersedes 和修复范围，不能继续把被否决截图作为合格结果。

交付分别记录：本地实现、技术检查、独立视觉/功能审核、用户认可、激活/部署。一个状态不能替代另一个。原生 Harness 工具的更严格门禁继续生效。

## 模块职责先于卡片差异

先说明各模块让用户完成什么、第一焦点是什么、信息量与占地是否匹配，再选择列数、卡片分组和视觉语言。优惠比较、商家发现、主题导航分别审核。禁止以颜色变化冒充设计差异，也禁止为了差异强行扭曲适用的阅读形态；禁止仅为两列齐底改变模块职责。手机长主标题需合理释放整行宽度。取证须包含完整页面、模块之间关系、同一模块短长内容和PC/手机，不能只裁单卡。Coupon详情的具体判断见 knowledge/imported/skills/coupon-detail-generation/references/detail-layout-methods.md。

## 专业改稿的模块语言检查

执行入口必须覆盖每个目标工程和每个详情模块，检查优惠／身份／日期三层信息、白或极浅卡底的对比度、手机图标或小组件页头，以及主券复制区真实构图差异。复制图标与导航箭头按行为区分。每个模块拥有适合任务的卡型，整页保留品牌一致性；可选齿孔、切角、齿轮等装饰不代替布局。长主标题须检查最终文字轨道，普通推荐固定容量、商家Logo至少70px，主券完整。对应具体方法见 knowledge/imported/skills/coupon-detail-generation/references/detail-layout-methods.md；以工程/模块/视口和实际证据逐项回填，未查不算通过。

## 全页面防错前移

在扩展页面前，按global-layout-baseline为每个实际卡型声明PC/手机预算，用真实短长数据实现一组并实测。再扩展调用页；交接前用最终routes核对全部启用页的PC/手机基础几何，独特模板/状态/极值及断点邻域独立看像素。隐藏模块、未映射路由或未执行项不得算通过；保留原生业务门禁。

## 商家字段轴线进入制作与审核覆盖

plan为每个商家家族声明Logo／名称／券数的轴及操作净距；make先用短长名称排一组；check与review逐字段核对盒和可见数字／单位文字，覆盖PC／手机／320px及换列两侧。上下中轴与横排文字组分别使用适用映射，不能只看卡框、宽高或CSS的center。按global-layout-baseline与detail-standard的商家轴线防回归执行；用户指出后完成源码修复，还须将故障样例、执行参数和新旧回放留在当前架构，历史冻结包保持原样。

自适应维护执行：先记录失败组件和已正确的保留样本；按global-layout-baseline的容量驱动方法选择构图。任务/模块声明reviewWidths和实际breakpoints，执行器展开±1；按问题声明六类adaptive criteria并冻结可执行预算。作者与独立审核均须绑定精确候选和逐宽度像素，不以端点代替中间宽度。维护不改未授权身份，不生成额外修复文档。

手机专项不能止于卡宽：按公共规则将标题右入口收为有名称图标，横滑箭头放实际内容两侧、不得独占一行；文章外框规则。真实源码接入共享资产或本站等价实现，冻结heading-action/rail-controls/image-fit.conventionalFrame并实际点前后、缩放往返和PC保留对照。

手机卡片按global-layout-baseline逐优惠/文章家族执行action-flow与image-fit.balanceWith/fitMode；日期与紧凑动作同排或完整footer，横排照片与完整阅读组等高。列全changed/preserved/not-present和真实样本，实际点击、照片解码及断点往返。一个站或featured样本不能覆盖其他家族；无像素证据不得放行。
