# Banner production in SiteFly

The installed `dsh-image-gen` plugin supplies `generate_image` and `edit_image` in the Web workspace and in new SDK runtimes explicitly started with `--image-plugin`. Check the actual available tools/preflight: existing or default SDK runs may not have them, and an installation alone does not prove provider authorization or successful output. The coding model continues to own website implementation; the configured image provider creates raster artwork. Do not call the Kimi coding endpoint for images, guess credentials, or claim that Codex's own image tool is available to the standalone Harness.

## Plan for the actual page

Follow [the owner's UI-first priority](homepage-visual-priority.md). New coupon homepages and explicitly rejected homepages require an original promotional visual; the author may not waive it by declaring a text-led direction. Before creating/selecting artwork, record its role in `source/docs/banner-assets.json`: route and placement, content subject, brand palette and medium, desktop/mobile displayed proportions, subject position, text-safe area, crop strategy and accessibility text. Use a per-asset entry; multiple routes can share an asset when appropriate. Choose photography, illustration, collage or a cutout to fit this site's design, not a universal shopping-bag template. Preserve accepted existing designs outside the requested scope; do not add Banners to forbidden detail regions.

Keep headings, offers and buttons as real HTML. Request artwork without baked-in words, discount claims, logos, fake UI or watermarks. Merchant logos must continue using official source files. Do not depict a fictional image as a verified merchant product or endorsement. Reference a website's layout without importing its industry into an unrelated coupon site.

## Generate and preserve

1. Call `generate_image` with a concrete prompt and supported dimensions/aspect ratio matching the planned placement. Omit a provider override unless the user selected it. Different providers expose different size controls; consult the actual tool schema. Do not make every site use the same Banner proportions or composition.
2. If the provider is unconfigured or authentication fails, report the exact configuration need without revealing keys. Direct the user to Settings → Plugins → Plugin configuration → Image generation. Continue independent layout work, but do not mark required generated artwork complete. Do not keep retrying a configuration error. When the task does not require a generated-image deliverable, suitable authorized assets or a finished original illustration can satisfy the visual direction after real-page review; record their actual origin. Typography alone, a small icon or merchant logos do not replace the required homepage promotional visual. If suitable artwork is still missing, keep this milestone incomplete instead of approving a weaker no-image direction. Never add a random stock photo.
3. Use the tool's returned `savedTo` path. Preserve that original; do not regenerate to solve a copying, packaging or crop problem. If only an attachment was returned, use the plugin's save-to-workspace capability before integration. A timeout or unknown outcome is not proof no image was produced: check the existing result before a fresh paid request.
4. Copy the selected original to `sourcePath/src/assets/` under a unique, site-specific filename. Never overwrite an existing accepted asset or write into V1, a frozen revision, preview or released ZIP. Record the exact prompt, provider, model, source filename, selected filename, dimensions and SHA-256 in the manifest. No credentials or authenticated download URLs belong in this manifest.
5. Integrate through this project's actual generator. Its standard asset copy loop includes `site.asset`, campaign assets and saving-tip images; an additional Banner needs an explicit copy in that project's generator if not already covered. Reference it in HTML with the existing site's asset-root helper, or from an included stylesheet. Do not rely solely on a remote URL, JS-only reference, `srcset` or inline CSS: the current offline exporter discovers `src`/`href`/`content` and stylesheet `url()` references. Verify the real ZIP contains every used image; adapt that project's exporter when required by responsive art direction.
6. Use `edit_image` for an intentional artwork revision, preserve the earlier original and record the replacement as a new candidate. Check the actual image and rendered page; tool success never establishes visual quality. SiteFly page acceptance still requires actual browser inspection even if the generic image plugin says no further file verification is needed.

## Review in context

For homepage visual direction and corresponding reviews, load [the owner's 2026-10-22 visual calibration](cases/owner-home-visual-calibration-20261022.md). Evaluate the header, Banner, first shopping group, action colors and category language as one composition. Preserve the approved quality and the site's selected direction; do not mass-reuse its palette, products or geometry. A compelling image does not waive header craft or demonstrate responsive website acceptance.

The independent `site_design_review` role checks image relevance, subject integrity, sharpness at rendered size, palette/lighting fit, hierarchy, text contrast, desktop/mobile crop, loading and offline availability. It also checks whether this is another site's same composition with a new picture. Compare images in the real page, not only the plugin's gallery. Preserve the required detail-page business framework; do not add Banners to forbidden regions.

Report missing/broken/mismatched imagery, obstructed actions, illegible text or destructive cropping as actionable findings under the existing visual/responsive/offline checks. A major defect yields `revise`; the generator adjusts the source and creates a new build for review. Never mark a generated candidate as aesthetically approved automatically.
