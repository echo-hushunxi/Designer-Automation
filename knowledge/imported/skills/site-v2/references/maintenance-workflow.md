# Existing-site maintenance: Web and SDK

Use this branch when the user asks to repair or refine an existing site. It preserves the current source, accepted identity and immutable outputs. It is not a new-site design brief.

1. Identify exact project IDs using compact status/inspect. Do not select by a similar name or an ambient preview URL. Pass the IDs and intent=preserve to workflow. Record the named regions, baseline build/delivery IDs, and a short affected-regression list. Missing or conflicting target identity requires clarification before writing.
   Save `source/docs/maintenance.json` with `{version:1,baselineBuildId,regions:[...],families:["detail",...],constraints:[...],regressions:[...]}` before building. The build verifies the current released baseline and freezes this scope for the reviewer. It does not waive any required check or apply new-design gates to an unchanged site.
   Homepage/card maintenance also freezes `source/docs/visual-modules.json` with version 1 and pages (family, artifact-relative route, modules). Each actual module/card family declares id, selector, cardFamily and real sampleCases with short/long/last-row roles; a single shared entity needs singleSampleReason. Native handoff and review require separate PC/phone/320px module observations, bound group/short/long/last-row pixel views and an independently reconciled actual module/card/sample inventory. A whole-page benchmark or geometry sweep cannot replace ordinary or seasonal card inspection. Existing immutable builds without this contract retain their frozen protocol.
   When examples establish a general defect across an authorized site batch, enumerate that entire batch's current builds and applicable home/detail/store hosts before repairing. Examples are not the whole target list. Reconcile every selected site as reproduced, already-correct or not-applicable with actual evidence; missing coverage stays not-run. Honor a later narrowed priority list, preserve its already-good samples and stop inspecting excluded historical sites. `status` supplies exact identities; pass the reconciled IDs to `workflow` instead of inferring scope from a single browser tab.
2. Load the project's Coupon entrypoints and applicable current references once. Compare resource hashes across a batch before rereading identical text. Read only needed source functions/selectors; do not dump minified CSS/HTML, whole catalogues, old review reports or complete project history. Use bounded extracts. Updated hashes or different contracts require a fresh read.
3. Reproduce the reported defect on representative packaged pages. Existing homepage artwork and design remain the baseline unless the owner requested a redesign. Do not repeat commercial reference research, image generation, novelty/cohort design matrices or homepage-direction approval for a scoped Logo/detail repair. Existing frozen gates still apply if a task actually changes direction or a new-design candidate is requested.
4. Make one coherent source repair batch per site, through its sole original author. Do not append layer after layer of CSS without reading the effective cascade. Build once after the scoped changes and source-level checks; build again only for an observed artifact defect or failed check. Report-schema mistakes are repaired in the saved draft, without another site build.
5. Self-check the changed families and affected regression states on desktop, phone and 320px; include tablet where the layout changes. View actual pixels and operate relevant code/deal/expired, copy/reload, search or client redraw states. Keep exact build/evidence IDs. Reuse a matching offline browser receipt for several checks in the same candidate when it actually covers them; do not repeat the same visit for every report field. Never reuse another author/reviewer receipt as your own observation or carry evidence to a different artifact.
6. Delegate one independent read-only review sweep for the scoped candidate. Check changed regions, applicable hard rules and affected regressions; record unrelated historic differences as baseline differences. Do not expand a Logo/detail task into a whole-site redesign. The reviewer makes its own actual observations and returns one consolidated packet. Repair together, then retest inherited issues and affected regressions on a new candidate. Do not stream ordinary findings into individual rebuilds.
7. Release only when the candidate's existing frozen acceptance requirements pass. Keep full data, artifact, browser and review records. Summary tool output is a context aid, never acceptance. Unchecked items remain not-run; do not trade correctness, visual inspection, independent review or offline evidence for a smaller token count.

## Context and scheduling

Use compact default tool results. detail=full explicitly requests complete metadata. Browser results retain artifact/evidence identity, viewport, clock and copy-check status; read fullResultPath for complete saved audit data when needed. View liveViewPath before judging the layout.

Batch independent reads/checks in one model step where the tools support it. Mutations, dependent browser interactions and build/review transitions stay sequential. A three-site maintenance batch shares factual data and identical rule text, not one combined growing design transcript or one mandatory card skin.

Track real provider-reported input/output/cache tokens separately and within the run's startedAt/runtimeExit boundaries; characters are only a payload-size measure. Cached context is still context and can incur provider cost, but is not new input. The shared preset uses the official durable semantic checkpoint at a new turn or successful persisted build/handoff/review boundary when existing context exceeds 60k tokens. The check considers both the text estimate and actual provider input since the last checkpoint, including image input; original history/session ownership remains intact. It never substitutes a new author or drops history while a tool pair is open. Missing usage is unknown. Do not lower model reasoning or change provider silently.

Use the same draft/evidence-ID report mechanics on maintenance builds, including workflow 1. Append observations instead of retyping all receipt metadata. Use short browser scenarios for known dependent actions, return an image at each visual decision point, and inspect controls/source before choosing selectors. A scenario performs real operations with one receipt per step; it does not judge the result. Query provenance with action=data instead of dumping it.

手机优惠/文章维护先列出授权站点内全部实际家族及保留样本，执行公共规则的action-flow与图文等高；生成、原生预算和独立审核使用同一selector。按精确最终候选逐家族复查，逐站更新preview及ZIP，禁止只看单站后概括全部。

阅读卡覆盖须展开实际首页、目录和文章内相关推荐三个调用位置，包含无图文字卡、空列表与正常纵排。初始HTML直接生成语义分组；用reading-static.mjs或等价纯生成逻辑，生成时assertReadingMarkup，home预算包含body[data-home-flow-static="1"]。实际执行JS开启、禁用/延迟、离线ZIP及320/375/393/断点±1/PC保留对照，任何漏项保持未检查。

商家/分类适配维护须把home、CID详情和SID商家页的嵌套宿主一起列入清单；检查实际展开宽度、正常窄侧栏、换列断点±1以及末行。先用packing/gapRange复现失败，再修原有有效级联；独立复查后只更新确有变更的站，已正确站保留候选和证据。
