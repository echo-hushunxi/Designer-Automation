# Shared generation workflow: Web and SDK

This is the same default workflow for a user typing directly in the SiteFly Harness workbench and for a batch coordinator. It applies to one new site as well as five. A short brief does not lower the visual standard. Do not depend on Codex follow-up prompts, private run inboxes, or a separate operator to supply references, reject weak UI, arrange review or continue repairs.

The owner explicitly adopted [the four-reference Coupon common craft standard](../../site-design/references/coupon-common-craft.md) for future Codex and Harness generation. workflow.couponCraft exposes the same version, rules and observation hashes in full and compact responses. New imports bind these resources and create an unresolved docs/site-craft.template.json; complete docs/site-craft.json with actual palette roles, four spacing layers, per-card space/action/phone decisions, density, responsive organization and fact checks before structure preflight. Preflight binds the craft plan; any plan/data change requires a new preflight. A shared standard preserves different visual identities, and observed dimensions are reference examples. Actual direction and full-site review still decide quality. Existing frozen projects keep their original requirements; scoped maintenance does not restart the entire design exercise.

Read every current entry in `ownerDesignRejections` before choosing an origin or reference. The owner's 2026-10-13 removal covers Clipwise, Savervine, eveandember-harness-20261008, merryperks-harness-20261008, Goodfind, DealDeck, Aislewise, Storeline, Gridly, Counterpart and Kindred Deals; previous bans remain effective. These are low-quality, unusable negative examples. Historical internal pass/ready reports cannot overturn the owner verdict or authorize recreation, renamed reuse, copied visual directions or promotion as a reference. Preserve the separate original eveandember/merryperks homepage baselines. Judge actual visual finish and practical shopping usability against the excellent references and those approved originals; technical success and difference alone do not qualify a site for expansion or delivery.

Identify the task before applying the new-site sequence below. Existing-site repair/refinement uses [maintenance-workflow](maintenance-workflow.md): compact status/inspect, exact IDs and workflow with intent="preserve" and projectIds. New-design reference study, novelty, original artwork and homepage-direction stages apply when establishing/replacing a direction, not to unrelated baseline regions in a scoped Logo/detail repair. The candidate's frozen gates still govern acceptance. Default tool summaries reduce context; detail="full" or browser fullResultPath exposes complete records. Never confuse smaller output with fewer acceptance requirements.

New candidate records use `reviewWorkflow: 2`. Before delegation the original author must call `site_harness handoff` with actual browser self-check evidence for the scoped families at 320px, a 321–414px phone and desktop. The reviewer uses the durable begin/collect/close and draft/validate/submit actions described in [review rounds](../../site-design-review/references/review-rounds.md). Ordinary builds cannot replace a collecting candidate; `diagnostic:true` builds remain separate and never qualify for delivery. Tools now preserve report evidence and repair findings; do not turn missing report fields into another site build. These checks constrain execution but do not prove aesthetic quality or standalone Web generation parity.

An inspectable candidate with failed author measurements still enters independent review. The public handoff defaults to recording the failed checks as `blockers` and returning `blocked-candidate-for-independent-review` with `reviewOnly:true`; actual actor-owned scoped browser coverage remains mandatory. Delegate the independent sweep automatically and close one `revise`/`blocked` packet. This is a real frozen candidate, not a `diagnostic:true` build. It cannot close `ready`, establish direction, pass or release. Repair limits stop further source changes; they do not cancel diagnosis or turn numeric checks into a visual verdict. Do not ask the user to approve routine entry to this failure review.

New-design projects imported with `generationGateVersion: 1` also freeze the build stage. Start with `site_harness(action="build", stage="homepage-direction")`; after author handoff the independent reviewer closes the entire homepage packet. Only its `ready` decision stores a direction approval bound to that exact artifact, receipt set and immutable packet. Then build with `stage="full-site"`. A homepage candidate cannot be handed off as full-site, receive final acceptance or release. A diagnostic candidate cannot enter either review stage. Historical projects keep their frozen workflow. These gates enforce sequence; the independent visual judgment remains necessary.

For full new-design/reference-rebuild rounds, the public coverage plan includes `requiredWidths` from the build's frozen `policy.viewports` for each page family. The author handoff and independent checked coverage must each provide their own exact-build visits at those widths, including tablet boundaries; one desktop/phone/narrow sample does not cover every policy width. Reuse existing visits and inspect only missing widths. Early homepage-direction and historical/maintenance scopes retain their existing band coverage; already-created round plans remain frozen.

For gated candidates every finding includes `violatesHardRule: true|false`, separately from `severity`. Confirmed hard failures also name the actual frozen `policy.hard` key in `hardRule`, for example `minimumHitAreaPx`. They block readiness and enter the consolidated repair packet even if severity is `minor`. Do not infer hit area from an outer form alone: operate and inspect the actual target. A classification field never replaces the real check.

1. **Bootstrap.** Call `site_harness(action="workflow")`, status and policy. Read the current site-v2/site-design/site-data skills and imported business skills. Keep the user's selected provider/model; never silently substitute one. Record workflow version/hash and actual tool capabilities in `source/docs/generation-context.json`. Required missing tools block the corresponding stage; installed image tools do not prove provider authorization. Existing sessions may have old tool/persona code: do not claim they hot-reloaded.
2. **Business preflight before composition.** Read workflow.couponFramework. Use the bound real public API data to write docs/site-structure.json (page types, modules, card fields, source and empty-state decisions). Call site_harness(action="preflight", projectId=exact ID) before implementing visuals. Newly bound projects cannot build without a matching actor/data/plan receipt. The plan fixes business responsibilities, not a common page skin. Existing projects retain their frozen scope unless explicitly adopted.

2. **Reference study.** The workflow response includes a shared reference pack, original capture dates, URLs, viewport/scroll metadata and hashes. Use read_image on available captures; label them historical capture-based observations, not a live visit or current offer evidence. Open the specified local Brightside/Tagtally builds yourself via site_browser on desktop and phone. If a local build is unavailable, select and record a suitable available local comparison; if no suitable reference evidence exists, obtain it before approving direction. Respect a user's supplied references. A Web user must not have to know the old batch directory or supply screenshots again. Learn shopping appeal, hierarchy, composition and coherent visual language; do not embed competitor artwork, copy their ads/overflow, or inherit unsupported claims.
3. **Creative design.** Establish a site-specific, original promotional visual and complete first two folds for US shoppers, plus representative store and coupon-detail cards. Design imagery, typography, palette, real buttons, card internals, grouping and mobile layout together. No fixed palette/radius/button or five-theme matrix. Share true data and stable behavior, not one visual template. Preserve title/description sizes, gaps, banned-content rules, recommendation counts and fixed detail business behavior. Do not invent discounts, codes, verified status or urgency.
4. **Image capability.** Inspect the actual tools. When generated raster imagery is required, use the configured Harness image plugin and record actual results; an unconfigured provider is a missing capability, not permission for random imagery or a text-only homepage. When appropriate and allowed, finished original illustration or authorized assets may satisfy the visual requirement after review. Never present a Codex-only image service as available to standalone Harness. Keep selected assets and provenance in the site's editable source and final ZIP.
5. **Homepage gate.** Build a representative homepage-direction candidate, self-inspect desktop and mobile, then automatically delegate to the independent read-only site_design_review role in a fresh context. Provide exact project/build IDs, reference pack, local comparison IDs and stage homepage-direction; provide no desired verdict. The reviewer views first, then reads the design plan. Preserve its unedited feedback with build identity in the run/project records. Only direction established permits full expansion; for gated projects this is the independent closed `ready` packet required by the full-site build tool. Revise goes back to the original author, then a new homepage candidate and fresh review. Not-run requires completing missing evidence. This is not a final pass.
6. **Complete and repair.** Expand an established direction to all required routes. Follow [consolidated review rounds](../../site-design-review/references/review-rounds.md): inspect the whole scoped candidate for actual visual finish, responsive layouts, interactions, facts, cohort differences where applicable, offline ZIP and old-site preservation; collect findings into one complete packet, then dispatch one author repair batch and retest all inherited issues plus affected regressions on the new candidate. Do not trigger rebuilds for individual discoveries while the sweep is ongoing. Only an issue preventing further inspection warrants an early blocking packet, after checking unaffected areas. Preserve reliable source and prior builds. Never relabel rejected artifacts, average away visual defects or equate technical checks with good UI.
   For code offers, use `site_browser copy-check` on the actual packaged page with the source-listed expected code. Verify native copying, a controlled `copyMode="fallback"` attempt and `copyMode="denied"` feedback. Inspect the resulting pixels, URL and action state; reveal must not navigate, and reload must restore the mask. The controlled modes temporarily exercise browser API failures and restore those APIs afterwards. They are branch checks, not evidence of a real LAN deployment or physical device. Preserve `copyCheck.mode` in review evidence and describe any untested delivery environment accurately.
7. **Deliver and disclose.** Release only after the existing final acceptance gates pass. Report previews, ZIPs and remaining limitations accurately. A candidate is not accepted; internal review is not owner approval. All reusable lessons from a supervised run belong in these shared skills, tools or reference materials, not exclusively in a private coordinator prompt.

## Prevent known defects during production

The workflow response also supplies `designMethods` with the local [creative craft adaptation](../../site-design/references/creative-craft.md), its content hash and verified upstream provenance. Read it when establishing or replacing a direction and record the hash alongside the workflow hash in `generation-context.json`. Both Web and SDK receive the same material without a private Codex brief. Apply the relevant methods to the existing plan, self-check and independent benchmark; no extra serial review stage is introduced. Existing sessions must call workflow again at their safe resume boundary to obtain it; a source edit does not prove they consumed it.

Before composition, load [production lessons](../../site-design/references/production-lessons.md) and select the relevant failure modes. Before handing a candidate to an independent reviewer, the author records actual viewport/route/state evidence for those items and repairs known major defects. Keep those observations in the run record, keyed by exact buildId. Each review cycle feeds proven general lessons back into the shared skill through the coordinator; site-specific visual choices stay local. Neither a checklist nor an established direction is final acceptance. This prevention loop applies equally to ordinary Web requests and SDK batches.

`productionLearning` now returns the production-lessons index and [human-correction capability pack](../../site-design/references/human-correction-learning.md), with actual paths, text and separate content hashes. Both normal compact and full workflow responses identify the same files. Authors record the applicable H01–H08 and concrete decisions before composition, then actual candidate evidence; reviewers use the frozen design-kit versions after independent first impressions. Updated application skills do not hot-reload running sessions or rewrite historical candidates. For new evidence policies with `prohibitedPresentationRequired`, every browser action records the known prohibited-content scan; failures or missing scans block author handoff, direction readiness and formal visual pass. This is an executable floor for known DOM patterns, not proof that all visual problems have become deterministic checks.

## Proving entry-point parity

Same preset/configuration is necessary but cannot guarantee identical model output or equally good aesthetics. Test from a fresh **Web workbench** conversation using a normal short site brief, without Codex supplementing the author with private instructions or repairing its final UI. Keep model/provider, facts and benchmark comparable. Verify it loads this workflow, studies the actual references, creates original artwork/composition, triggers independent homepage review, repairs rejection and completes final acceptance. Record visual and process results separately. Until that Web run passes, report configuration alignment as implemented and quality parity as unverified. Differences in UI polish must be repaired in the shared workflow or author/reviewer capabilities, not hidden with operator-only patches.
