# Consolidated review rounds

If `begin` returns `reviewOnly:true`, the author handed off an inspectable candidate with failed measurements. Keep `handoffBlockers` visible, inspect the actual scoped pixels and remaining unaffected actions, and close one failure packet. A failed numeric preflight does not replace visual diagnosis. This candidate cannot close `ready` or be accepted; the original author must resolve blockers on a new candidate. Missing actor-owned author coverage still prevents entry. A source-repair budget never prevents this read-only sweep.

## Durable tool workflow (reviewWorkflow 2)

New builds advertise `reviewWorkflow: 2` in `site_review context`. Use the following actual tools; do not replace them with prose in a coordinator message. Historical builds keep their frozen final-report schema and may opt into collection without rewriting history.

If context also reports `generationGateVersion: 1`, the frozen `stage` must match the review scope. A homepage-direction candidate cannot receive a full-site report. Closing its independently checked `ready` packet establishes direction only; the author then creates a new full-site candidate for complete acceptance. Every finding in a gated round must include `violatesHardRule: true|false` independently of severity. A confirmed hard failure names the frozen `policy.hard` key in `hardRule` and must be repaired even when labeled minor. For an explicit business-contract violation use the relevant `requiredChecks` rule and describe the exact contract clause. Optional visual polish remains minor with `violatesHardRule: false`. Do not use this classification as a substitute for operating and measuring the actual page.

1. The original author uses `site_harness(action="handoff", projectId, buildId, payload=<JSON>)` with `{scope:"homepage-direction"|"full-site",summary,visits:[{evidenceId,family,observation}]}` after actual visual self-check. Each scoped family needs desktop (>=1024), phone (321–414), and 320px evidence. Homepage scope needs home; full scope needs home/store/listing/detail. Known major failures should be fixed before handoff. This admission is not independent acceptance.
2. The dedicated reviewer calls `site_review(action="begin",...,payload={scope})`. The returned `plan` is the coverage checklist. Repeating begin with the same owner/scope resumes it without erasing findings.
3. Record incremental observations with `collect`. Payload fields are optional: `coverage:[{id,status:"checked"|"blocked"|"not-applicable",observation,visits:[{evidenceId,family,observation}],blockedBy?}]`, `defects:[{id,severity,route,width,state,description,impact,adjustment,retest,evidenceIds}]`, `benchmark`. IDs upsert existing entries, never dispatch a repair. Blocked means a real blocking defect prevents inspection, not ordinary visual imperfection. Not-applicable is limited to explicitly optional source states.
4. `site_review(action="evidence",...,payload={offset:0,limit:50})` returns your real immutable receipt IDs/route/viewport/time/frame paths. Use it instead of delegating log parsing or inventing IDs from session directories.
5. After every planned entry is accounted for, `close` with `{decision:"ready"|"revise"|"blocked",summary}` emits a single durable packet. `ready` means ready to assemble the formal report, never accepted. Source repairs inherit all hard-rule/major/blocking IDs even if the old formal report has not been submitted. A closed rejection cannot become ready on the same build.

   A homepage-direction build may inherit repair requests from an older full-site round. Keep every original plan item and request. Only a repair whose frozen canonical route identifies a known inner page may use `status:"deferred-to-full-site"`, an explicit not-run observation and empty visits. The server classifies the frozen request, not caller-supplied route metadata. Home, peer/global, unknown-scope and base checks cannot be deferred. Closing records the complete deferred requests and a direction-only scope limitation. Full-site collect and close reject this status; every inherited repair remains mandatory there. Deferred never means checked, passed or not applicable.
6. Save report sections with `draft`. The only payload keys are `visits`, `referenceVisits`, `checks`, `defects`, `firstImpression`, `designReview`, `contentReview`, `comparisons`. Keep `buildId` in the tool arguments; build identity, artifact hash and reviewer are filled by the tool. Visits need only `{evidenceId,family,state,observation}`: route, viewport, artifact hash, simulated clock and copy-check values are loaded by the tool from the immutable receipt. Use complete tool-issued IDs. Nested `visit`, `referenceVisit` and `visits` may use evidence IDs instead of numeric indices; they are resolved at validation/submission. Arrays/sections **replace**, not append: when adding one visit, send the full saved visits array plus the new entry. Read the saved draft with an empty payload if needed; avoid concurrent edits to the same section. Formal defects need numeric `width` (for example `390`, not `"390"`, `"all"`, `"320–1440"` or a `viewport` field), plus `state`, `impact`, `adjustment`, `retest`; describe additional affected widths in the finding text.
7. Call `validate` then `submit` without a `review` argument to use the saved draft. Validation errors are report corrections; keep inspecting/repairing the report on this build. Do not request a source rebuild just to satisfy report formatting.

These draft/evidence mechanics also apply to workflow 1 maintenance reports. `appendVisits` and `appendReferenceVisits` append/upsert only newly observed `{evidenceId,family,state,observation}` records under the reviewer-owned lock, without resending prior visits. Do not combine append and replace for the same section. Full receipt fields are hydrated and judgments remain your explicit observations; no check is automatically marked pass.

The current tool also checkpoints a parseable full `review` before validation, after checking its build/hash and independent reviewer identity. If submission fails, its error states that the report is saved. Read it with `draft` and an empty payload, patch only the wrong sections, then validate/submit without `review`; do not regenerate a large report. Each inline attempt is retained separately and saving never accepts a report or changes its evidence claims. Malformed JSON and mismatched build/hash cannot become drafts. Older running tools need a safe idle-boundary reload before this recovery behavior is available.

Ready packets require a separate `benchmark` judgment: `{references:[{source,observation},...],dimensions:{hero,firstTwoFolds,typography,imagery,cardsAndActions,mobile}}`. Each dimension is `{level:"below"|"meets"|"exceeds",observation,evidenceIds}`. Independently look at at least two named references (including an owner-approved local design where available), identify the actual quality comparison, and bind the current candidate evidence. Any `below` or unmeasured dimension blocks readiness. These are accountable judgments, not objective scores; never fill `meets` to satisfy the schema. Style differences alone do not answer these questions. For each dimension explain specific hierarchy, composition, image integration, finish or interaction affordance, not adjectives.

For candidates with frozen `visualCalibration`, the current four owner-selected sources are mandatory. Use each exact URL/domain in `benchmark.references` and actually inspect all provided desktop/phone first-two-fold images with `read_image`. Ready/submit checks the independent reviewer's successful image attachment hashes, not author prose or a count of source labels. An `external-references: never supplied` placeholder is not an observed benchmark. This evidence gate does not prove good design: the images must still support an honest aesthetic comparison. Same-version image reads by this reviewer may be reused without replay.

During `collecting`, an ordinary build cannot replace the candidate. An original-author `diagnostic:true` build may help investigate but never advances currentBuild or accepts/releases. Do not mutate the frozen candidate. Remove diagnostic code/time before creating the next normal build after packet closure.

Apply this orchestration to both Web and SDK generation. The owner requires collecting as many issues as possible in one review, not streaming individual defects into repeated author rebuilds. It changes scheduling, not the frozen artifact's acceptance criteria.

## One candidate, one complete finding set

At the start, record round ID, exact build/hash, review scope and a coverage checklist derived from the frozen contract. For a homepage-direction round, inspect the complete first-two-fold scope on desktop/phone plus applicable boundaries and references. For a full-site round, cover every required page family, responsive sizes, initial and changed interaction states, facts, peer comparisons and offline behavior. Use representative cases with actual evidence; distinguish inspected cases from untested routes rather than claiming every URL was visited.

When a plan item lists `requiredWidths`, its checked visits must include your own exact-build receipts at every listed width and matching page family. Desktop items may include tablet widths such as 768px as well as the ordinary desktop band. These widths come from the frozen policy, not from a new shared skin. Reuse receipts already collected and group missing views into short scenarios; do not replay all interactions or rebuild to fill this coverage gap. Historical round plans without this field keep their frozen requirements.

Continue the checklist after discovering a defect. Record findings as they arise, but send the author **one consolidated repair packet after the scoped sweep**, not one task per finding. The coordinator must not initiate source changes, new builds or candidate switching while that same project's review sweep is still collecting issues. Other projects may progress independently. Keep peer comparison IDs explicit; if a peer changes, refresh affected comparisons near final acceptance rather than restarting the whole audit for every intermediate peer build.

Before handoff, account for every scoped check as checked with evidence, genuinely not applicable with reason, or not-run with a specific blocker. The packet contains:

- Stable defect IDs, severity, affected routes/components, viewport/state, actual evidence, user impact, desired outcome and retest condition.
- Grouped shared causes where supported; one common card defect can cover multiple observed routes without turning each into a separate repair cycle.
- Hard failures, visual defects and optional polish clearly separated; settle applicable polish in this packet instead of adding it piecemeal afterward.
- Coverage, untested cases and capability blockers; unresolved not-run requirements still block verified delivery.

A navigation failure, broken rendering or crash that actually prevents the remaining inspection may justify an early blocking repair. First inspect all unaffected areas, collect every currently observable issue, identify exactly what is blocked, and send one blocking packet. Ordinary spacing, overflow, copy, logo fit or card styling defects are not reasons to interrupt the sweep if inspection can continue.

## One repair delivery, one consolidated retest

The original author receives the closed packet, fixes its applicable items together, and self-checks the affected page families and states before handing off one new candidate. Local diagnostic builds are allowed, but are not automatically sent to the reviewer as new candidates. Remove diagnostic clocks/scripts/content before final candidate creation. Preserve original source history and frozen artifacts.

The same independent reviewer checks **every inherited defect**, then regressions in changed components and related flows, plus any previously blocked checks. Verify source/build identity and refresh the necessary unchanged-baseline evidence under the frozen schema; do not rerun unrelated exploration without a reason. Return the remaining issues together. Label each as unresolved original defect, repair-induced regression, previously blocked issue, or missed first-round issue, with evidence. Do not suppress real new defects to claim one-round success; use missed coverage to improve the next initial sweep.

Homepage-direction and full-site acceptance remain distinct scopes; they are not permission to split one full-site audit into arbitrary batches of findings. An established homepage does not approve inner pages. Do not promise all aesthetic work can pass in exactly one round. After three unsuccessful focused repair rounds, preserve the consolidated unresolved list and investigate the repeated cause; do not loosen acceptance or blindly repeat the same loop.

## Report mechanics must not become a repair loop

Keep an evidence index during inspection using tool-issued IDs, route, viewport, clock and observed state; a session hash is not an individual receipt. Assemble the report from that index. Schema rejection is a report error, not a new site defect or reason for an author rebuild. Correct the specific report mapping while preserving its honest verdict. For a rejected candidate, a complete consolidated finding packet with explicit unsubmitted status can initiate repair without repeatedly regenerating a giant final-pass report; final delivery still requires the full valid review and real evidence. Never label incomplete coverage, a failed submission or a candidate build as accepted.

## Existing work when adopting this rule

Keep already authorized edits and sole-author ownership. Do not roll back or duplicate work merely to create a clean round. Stop adding individual new repair tasks; collect subsequent findings into the next consolidated packet. Mark the ongoing pre-transition edits in the round record, finish their author self-check, then freeze the review candidate. The coordinator closes the collection phase before dispatching any further repair batch.
